# AGENTS.md — lusakey

Инструкции для агентов (и людей), работающих в этом репозитории. Держите этот файл в актуальном состоянии по мере продвижения — особенно секции «Статус» и «Известные пробелы».

## Что это за проект

Кроссплатформенный (Windows/macOS/Linux) локальный менеджер паролей со встроенным TOTP-генератором (аналог Google Authenticator). Одна кодовая база на C++/Qt6. Хранилище — единственный зашифрованный файл на устройстве, без облака, без аккаунтов, без серверов. Между устройствами — только ручной экспорт/импорт зашифрованного файла. Дизайн — в стиле Claude.ai (тёплая палитра, терракотовый акцент).

## Зафиксированные архитектурные решения (не пересматривать без явного запроса пользователя)

- **Стек:** нативный C++20/Qt6, не Electron/Tauri/webview.
- **UI-слой: Qt Quick/QML**, не Qt Widgets. Выбрано пользователем осознанно ради скорости итерации по кастомному дизайну — несмотря на то что Telegram Desktop (эталон «одна кодовая база под 3 ОС») исторически рисует UI вручную на Widgets. Не переключать на Widgets без явного запроса.
- **`libs/core` не имеет ни одной зависимости от Qt.** Жёсткое правило: весь код в `libs/core` компилируется и тестируется без Qt. Это то, что позволяет `nmhost` (будущему native-messaging-host для браузерного расширения) переиспользовать `VaultService` без переписывания.
- **Синхронизация — только локально + ручной экспорт/импорт.** Никакого облака, никаких аккаунтов, никаких серверов.
- **Браузерное расширение не реализуется**, но шов (`VaultService` + `libs/ipc`) существует и компилируется уже сейчас (`nmhost/`, флаг `LUSAKEY_BUILD_NMHOST`, выключен по умолчанию).
- **Криптография:** libsodium — Argon2id (KDF) + XChaCha20-Poly1305 (AEAD). Не менять без явного запроса — обоснование в `docs/VAULT_FORMAT.md`.
- **Формат хранилища — key-wrapping (v2), не «пароль напрямую шифрует тело».** Реальный ключ шифрования тела (DEK) генерируется случайно один раз при создании хранилища и никогда не выводится из пароля напрямую. Он «оборачивается» (AEAD-шифруется) отдельно под каждый «слот»: обязательный слот пароля и опциональный слот восстановления (контрольные вопросы) — оба оборачивают один и тот же DEK, поэтому у хранилища может быть больше одного способа разблокировки без повторного шифрования тела при добавлении/смене слота. Тот же паттерн, что у LUKS/BitLocker. См. `libs/core/vault/vault_file.h` (`KeySlot`, `unwrapDek`, `makeKeySlot`) и `docs/VAULT_FORMAT.md`.
- **Восстановление по контрольным вопросам — осознанный компромисс безопасности.** Ответы на контрольные вопросы принципиально более слабый секрет, чем мастер-пароль (более узкое пространство перебора, социальная инженерия). Реализовано по явному запросу пользователя, а не по умолчанию — количество вопросов пользователь задаёт сам (минимум 1, без верхнего предела кроме санитарного кэпа в `vault_file.cpp`). Ответы нормализуются (обрезка пробелов + lowercase ASCII) перед выводом ключа — не путать с полноценным Unicode case-folding (кириллица не приводится к одному регистру, только обрезаются пробелы).
- **TOTP:** RFC 4226/6238, совместимость с `otpauth://`. HMAC-SHA1 — вендоренная реализация (её нет в libsodium), HMAC-SHA256/512 — через libsodium напрямую.
- **Отложенный компромисс:** поля `Entry` (`title`/`username`/`password`/`url`/`notes`) — обычный `std::string`, не `crypto::SecureBuffer`. `SecureBuffer` зарезервирован для ключа хранилища (единственный секрет, расшифровывающий всё сразу). Полностью SecureBuffer-based модель записи была признана слишком рискованной без компилятора под рукой в сессии, где это писалось — см. комментарий в `entry.h`.

## Структура репозитория

```
lusakey/
├── libs/core/     # крипто, формат хранилища, TOTP, VaultService — БЕЗ Qt
│   ├── include/lusakey/core/{crypto,totp,vault,util}/*.h   # публичный API
│   └── src/{crypto,totp,vault,util}/*.cpp                   # реализация + внутренние заголовки (sha1.h, hmac_sha1.h, base32.h — не публичные)
├── libs/qr/       # обёртка над zxing-cpp (импорт TOTP QR из файла изображения); собирается только вместе с app
├── libs/ipc/      # фрейминг native-messaging (Chrome/Firefox), без Qt, собирается всегда
├── app/           # Qt Quick GUI-приложение (LUSAKEY_BUILD_APP=ON)
│   ├── bridge/    # AppController, VaultListModel, ActivityEventFilter — C++/QML мост
│   └── ui/        # Theme.qml + components/ + screens/ + Main.qml
├── nmhost/        # заглушка native-messaging host (LUSAKEY_BUILD_NMHOST=ON, выкл. по умолчанию)
├── tests/core/    # Catch2-тесты для libs/core (без Qt)
├── tests/ipc/     # Catch2-тесты для libs/ipc
├── resources/fonts/   # Inter/JetBrains Mono — файлы шрифтов сюда нужно скачать вручную, см. README там
├── packaging/{windows,macos,linux}/   # Inno Setup / Info.plist+entitlements+notarize.sh / .desktop+AppImage
└── docs/VAULT_FORMAT.md   # точный байтовый формат файла .lusakey
```

- Дымовой запуск `lusakey.exe` (после фиксов ниже): приложение стартует без единой ошибки/предупреждения в stderr, кроме ожидаемых предупреждений про отсутствующие файлы шрифтов. **Не проверено визуально/интерактивно** — реальный внешний вид (цвета, шрифты, раскладка, анимации, сам флоу восстановления) никто не смотрел глазами; смок-тест был безголовым (только лог, без скриншотов).

- **QML-грабли, найденные при добавлении recovery-флоу (актуально для любого нового `Dialog`):** (1) не называйте функцию в QML-типе `reset` — это имя конфликтует с уже существующим сигналом/методом `Dialog`/`Popup`, QML падает при загрузке с «invalid override of property change signal or superclass signal»; (2) не присваивайте `implicitWidth` напрямую `ColumnLayout`, используемому как `contentItem` диалога — это создаёт binding loop с внутренней логикой `Popup`; вместо этого задавайте `width` на самом `Dialog`.

Для установки тулчейна на Windows см. `scripts/windows/setup-toolchain.ps1`.

## Сборка и тесты

Требования: CMake ≥3.25, компилятор с C++20, [vcpkg](https://github.com/microsoft/vcpkg) (`VCPKG_ROOT` в переменных окружения), Ninja, Qt 6.5+ (для сборки GUI).

```sh
# Только ядро (без Qt) — крипто/TOTP/VaultService/ipc и их тесты:
cmake --preset windows-x64   # или linux-x64 / macos-arm64 / macos-x64
cmake --build --preset windows-x64
ctest --preset windows-x64

# Полностью, включая GUI (нужен установленный Qt6):
cmake --preset windows-x64 -DLUSAKEY_BUILD_APP=ON -DCMAKE_PREFIX_PATH="C:\Qt\6.7.3\msvc2019_64"
cmake --build --preset windows-x64
```

**Windows-специфичная ловушка:** нужен активный окружение MSVC (`vcvars64.bat`) для компилятора/Ninja, но `vcvars64.bat` сам выставляет свой `VCPKG_ROOT` (на vcpkg, встроенный в VS Build Tools) — переустанавливайте `$env:VCPKG_ROOT` на свой vcpkg **после** импорта vcvars, иначе получите «this vcpkg instance requires a manifest with a specified baseline» от чужого, не настроенного под этот проект vcpkg.

## Формат хранилища

Полная спецификация — в `docs/VAULT_FORMAT.md` (актуализировать при следующем изменении формата — сейчас там ещё может быть описание v1, код уже на v2). Кратко (v2, key-wrapping): один файл `.lusakey`, заголовок в открытом виде целиком передаётся как AAD тела. Тело шифруется случайным DEK (не паролем напрямую); DEK «обёрнут» отдельно в каждом слоте — обязательном слоте пароля и опциональном слоте восстановления, оба оборачивают один и тот же DEK через `crypto::aeadEncrypt`/`unwrapDek`. Плюс BLAKE2b-чек-сумма для дешёвой детекции порчи файла до попытки расшифровки. KDF (Argon2id) выполняется только при создании слота (создание хранилища / смена пароля / настройка восстановления) — рутинное сохранение (`vault::writeVault`, из `VaultService::save()`) переиспользует уже развёрнутый DEK и существующие слоты как есть, лишь генерируя новый nonce для тела — иначе Argon2id на каждое сохранение убил бы отзывчивость UI.

## Дизайн-система (стиль Claude)

Реализовано в `app/ui/Theme.qml` (singleton). Цвета **проверены онлайн** (не выдуманы) — два независимых источника (mobbin.com, color-hex.com) сошлись на одних и тех же извлечённых с claude.ai значениях: фон «Pampas» `#F4F3EE`, серый «Cloudy» `#B1ADA1`, акцент терракотовый «Crail» `#C15F3C`. Реальный Claude — тёплый кремовый фон, не чисто-серый; `Cloudy` используется как заметный серый тон для сайдбара/границ (`bgBase`/`borderDefault`), раз пользователь просил именно серый. Остальные шаги палитры (hover/pressed, disabled, тёмная тема) — интерполяция поверх этих трёх якорных цветов силами проекта, не независимо подтверждены отдельно. Полный список токенов — читайте сам `Theme.qml`, это единственный источник правды.

Шрифты — **Inter** (UI) и **JetBrains Mono** (пароли/TOTP-коды, обязателен для разборчивости) как открытые аналоги проприетарных Styrene/Tiempos. Файлы шрифтов лежат в `resources/fonts/` (скачаны, не просто задокументированы — см. README там).

**Правила:**
- Никогда не использовать «голые» `SpinBox`/`Switch`/`CheckBox`/`Slider` из `QtQuick.Controls.Basic` — у них дефолтный белый/платформенный вид, не связанный с `Theme`. Использовать темизированные обёртки `app/ui/components/{AppSpinBox,AppSwitch,AppCheckBox,AppSlider}.qml` (тот же паттерн, что `AppButton`/`AppTextField`). Если нужен новый тип контрола из QQC2 — заводить для него такую же обёртку.
- **Никаких эмодзи и текстовых Unicode-символов вместо иконок** (не `"🔒"`, не `"✓"`, не `"✕"`). Все иконки — маленькие `Canvas`-компоненты в `app/ui/components/` (`EyeIcon`, `LockIcon`, `WarningIcon`, `CloseIcon`, `CheckIcon`), рисующие векторный глиф через `getContext("2d")` с цветом из `Theme.*` (`strokeColor`/аналогично). Новую иконку — заводить так же, а не эмодзи/символом.
- **Без градиентов** — только плоская заливка (`color:`), тонкие бордеры вместо теней/градиентов, кроме `MultiEffect`-тени на плавающих поверхностях (диалоги) — это не градиент.

## Конвенции для агентов, работающих в этом репозитории

- Не добавлять зависимость от Qt в `libs/core` ни при каких обстоятельствах.
- Публичный API `libs/core` — обычный C++ (`std::` типы), никаких Qt-типов в сигнатурах.
- Внутренние детали реализации (SHA-1, HMAC-SHA1, Base32, zxing-cpp) — не выносить в публичные заголовки `include/lusakey/core/...`.
- Новый код в `libs/core` — покрывать тестами Catch2 в `tests/core`; для TOTP/крипто сверяться с официальными тестовыми векторами, а не только ручным round-trip.
- Секреты (мастер-пароль, производный ключ) — только через `crypto::SecureBuffer`; поля `Entry` — сознательное исключение, см. «Отложенный компромисс» выше.
- В QML — всегда через `Theme.*` (цвета/шрифты/отступы/радиусы), никогда не хардкодить hex-цвет или пиксельный размер напрямую в экране/компоненте.
- В `Dialog`/`Popup`-производных QML-типах: не называть свои функции `reset` (конфликтует с сигналом/методом базового класса) и не присваивать `implicitWidth` напрямую `contentItem`, если это `ColumnLayout`/другой Layout-тип (binding loop с `Popup`'s implicit-size негоциацией) — задавать `width` на самом `Dialog`. См. `RecoverySetupDialog.qml`/`GeneratorDialog.qml`.
- При закрытии любого пункта из «Известные пробелы» — вычеркните его из списка и обновите статус вехи, если это её разблокирует.
- **Визуальная проверка UI без риска для реального хранилища**: `AppController::defaultVaultPath()` читает переменную окружения `LUSAKEY_TEST_VAULT_DIR` — если задана, хранилище создаётся/открывается там вместо реального профиля пользователя. Так можно безопасно создать одноразовый тестовый vault, поскриптовать клики через `user32.dll`/`SetCursorPos`+`mouse_event` из PowerShell и сделать скриншот окна (`GetWindowRect` + `System.Drawing.Graphics.CopyFromScreen`) для реальной визуальной проверки, а не только компиляции. `QT_QSTANDARD_PATHS_TEST_MODE_ON=1` (стандартный механизм Qt) **не сработал** на этой машине/версии Qt — не тратить время, сразу использовать `LUSAKEY_TEST_VAULT_DIR`. Всегда `Stop-Process` предыдущий `lusakey.exe` и удалять тестовую директорию перед новым прогоном — два процесса, указывающих на один и тот же файл хранилища, могут повести себя непредсказуемо. Известный при этом найденный и исправленный баг: `ScrollBar` с `policy: AsNeeded`, вручную подключённый к пустому `ListView` (0 строк), рисовался на всю высоту вместо того чтобы быть скрытым — понадобился явный `visible: listView.contentHeight > listView.height` (см. `VaultListScreen.qml`).
  - **Всегда вызывать `SetForegroundWindow(hwnd)` (+ небольшая пауза) прямо перед каждым скриншотом.** Без этого `CopyFromScreen` иногда захватывает совсем другое окно (например, видео в браузере), которое физически оказалось поверх lusakey в это мгновение на этом экране — `GetWindowRect` при этом возвращает совершенно нормальный, ожидаемый прямоугольник, так что подмена не бросается в глаза сразу, только по содержимому картинки.
  - **Мнимые «падения» между отдельными вызовами инструментов** — если разбить ожидание/повторные попытки на несколько раздельных вызовов PowerShell, `lusakey.exe`, запущенный через `Start-Process` в одном вызове, иногда пропадает к следующему вызову (`Get-Process` его не находит), хотя реального краша нет — подтверждено: тот же сценарий, отслеженный непрерывно (`for`-цикл с `Start-Sleep` внутри ОДНОГО вызова) на 90+ секунд, ни разу не воспроизвёл проблему. Разбивать длительное ожидание на несколько раздельных вызовов инструмента не стоит — либо ждать нужное время одним вызовом, либо не полагаться на то, что процесс переживёт границу между вызовами.
  - **`ui/welcomeShown` в `QSettings` — НЕ путь к хранилищу**, `LUSAKEY_TEST_VAULT_DIR` на него не влияет; см. пункт про `WelcomeScreen` выше.
