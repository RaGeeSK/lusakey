# Формат файла хранилища `.lusakey` (v2, key-wrapping)

Реализация: `libs/core/include/lusakey/core/vault/vault_file.h`, `libs/core/src/vault/vault_file.cpp`.

Один файл на хранилище. Все многобайтовые целые — little-endian. Формат переменной длины (из-за произвольного числа контрольных вопросов), парсится последовательно (`Reader`/`Writer` в `vault_file.cpp`), а не по фиксированным смещениям, как в v1.

## Идея: DEK + слоты (как LUKS/BitLocker)

Тело хранилища шифруется случайным **DEK** (Data Encryption Key, 32 байта), сгенерированным один раз при создании хранилища — **не** выведенным из пароля напрямую. DEK «оборачивается» (AEAD-шифруется) отдельно в каждом **слоте**:

- **Слот пароля** (обязательный) — ключ обёртки выводится из мастер-пароля через Argon2id.
- **Слот восстановления** (опциональный) — ключ обёртки выводится из ответов на контрольные вопросы (нормализованных и склеенных через `\x1F`).

Оба слота оборачивают **один и тот же DEK** — поэтому у хранилища может быть несколько независимых способов разблокировки без повторного шифрования тела при добавлении/смене слота (только слот пересобирается заново). Тело пересохраняется на каждое изменение записей, но слоты — только когда меняется сам пароль/восстановление.

## Байтовая раскладка (последовательная, не фиксированные смещения)

```
magic[8]                       "LUSAKEY\0"
version u16                    = 2
kdfAlgId u8                    1 = Argon2id
aeadAlgId u8                   1 = XChaCha20-Poly1305-IETF

-- слот пароля (KeySlot) --
memoryKiB u32, iterations u32, parallelism u32   (Argon2id для этого слота)
salt[16]
nonce[24]                      (nonce, которым обёрнут DEK)
wrappedDek[48]                 (AEAD_encrypt(DEK) = ciphertext(32) || tag(16))

-- слот восстановления --
recoveryEnabled u8             0 или 1
если recoveryEnabled:
    questionCount u8
    для каждого вопроса: questionLen u32 + questionText (UTF-8, plaintext)
    memoryKiB/iterations/parallelism, salt[16], nonce[24], wrappedDek[48]   (тот же KeySlot layout)

-- тело --
bodyNonce[24]
ciphertextLen u32
ciphertext[ciphertextLen]      AEAD_encrypt(DEK, bodyNonce, payload) = ciphertext || tag(16)

checksum[32]                   BLAKE2b-256 от всех байт выше (заголовок + ciphertext)
```

Заголовок (всё, кроме `ciphertext` и `checksum`) — единственная открытая часть файла, и он же целиком передаётся как **AAD** в AEAD-шифрование тела, поэтому подмена любого поля (версии, параметров любого слота, вопросов, nonce) детектируется при расшифровке тела через несовпадение тега.

**Тексты контрольных вопросов — открытым текстом.** Это осознанное решение: реальные флоу восстановления показывают вопрос до того, как введён ответ, а сам вопрос не секрет. Секретны только ответы (участвуют лишь в выводе ключа обёртки, нигде не хранятся).

`checksum` — не граница безопасности (это делает тег AEAD на уровне тела/слотов), а дешёвый способ отличить «файл повреждён/обрезан» от «неверный пароль/ответы» ещё до попытки расшифровки: `readRaw()` проверяет чек-сумму сразу после чтения и бросает `ChecksumMismatch`, не трогая крипто-примитивы слотов.

`payload` (расшифрованное тело) — версионируемая бинарная структура: метаданные хранилища + список записей (заголовок/логин/пароль/URL/заметки/теги/папка/TOTP-секрет+алгоритм+цифры+период/временные метки). Никакая структура (даже количество записей) не видна в зашифрованном файле.

### Внутренняя структура `payload` (`VaultModel::serialize`/`deserialize`, `vault_model.cpp`)

`payload` — отдельный, вложенный бинарный формат (версионируется независимо от заголовка хранилища через свой `kModelFormatVersion`):

```
modelVersion u32
nextEntryId u64
nextFolderId u64

-- реестр папок --
folderCount u32
для каждой папки: id u64, name (строка: len u32 + UTF-8 байты)

-- записи --
entryCount u32
для каждой записи: id u64, title/username/password/url/notes (строки),
    tagCount u32 + теги (строки),
    hasFolder u8, если 1: folderId u64,
    hasTotp u8, если 1: secret (bytes: len u32 + байты), algorithm u8, digits u32, periodSeconds u32,
    createdAt u64 (unix-секунды), modifiedAt u64
```

Папка — плоский, ненумерованный (без вложенности) реестр `{id, name}`; `Entry::folderId` — просто ссылка на такой id (или отсутствует). Удаление папки (`VaultService::removeFolder`) не удаляет ссылающиеся записи — оно их «осиротевает» (сбрасывает `folderId`), поэтому в бинарном формате нет отдельного шага каскадного удаления — только запись обновлённых записей при следующем `save()`.

## Ключевые функции (`vault_file.h`)

- `readRaw(path)` — читает и валидирует файл (magic/версия/чек-сумма), без пароля/ответов.
- `unwrapDek(slot, secret)` — выводит KEK из `secret` (пароль или склеенные нормализованные ответы) и разворачивает `slot.wrappedDek`. Бросает `AuthenticationFailed` при неверном секрете.
- `makeKeySlot(dek, secret, kdfParams)` — создаёт новый слот: свежая соль/nonce, KEK из `secret`, DEK обёрнут под него. Используется и для слота пароля (создание/смена пароля), и для слота восстановления (настройка вопросов) — операция идентична.
- `decryptBody(raw, dek)` — расшифровывает тело уже развёрнутым DEK.
- `writeVault(path, dek, passwordSlot, recoveryEnabled, questions, recoverySlot, payload)` — пересобирает файл целиком: свежий nonce тела, существующие слоты передаются как есть (без повторного KDF) — это и есть «рутинное сохранение».
- `createNew(path, password, kdfParams, payload)` — удобная обёртка: генерирует DEK, строит слот пароля, вызывает `writeVault` без восстановления.

## Экспорт/импорт

«Экспорт» — копия файла `.lusakey` целиком (он уже полностью зашифрован и самодостаточен). «Импорт» — открытие стороннего `.lusakey` файла его собственным паролем, дальше — слияние или замена текущего хранилища на уровне `VaultService`.

## Восстановление по контрольным вопросам

`VaultService::setupRecovery(questions, answers, kdfParams)` — требует разблокированное хранилище; количество вопросов задаёт вызывающая сторона (UI), не меньше одного. Ответы нормализуются (`normalizeAnswer`: обрезка ASCII-пробелов + lowercase ASCII — **не** полноценный Unicode case-folding, кириллица регистронезависимо не сравнивается) и склеиваются через `\x1F` в один "пароль" для Argon2id. `VaultService::unlockWithRecoveryAnswers(path, answers)` — альтернативный вход, не требующий мастер-пароля. `VaultService::hasRecovery(path)`/`getRecoveryQuestions(path)` — статические, читают только заголовок, не разблокируя хранилище.

**Осторожно:** контрольные вопросы — существенно более слабый секрет, чем мастер-пароль (уже пространство перебора, риск социальной инженерии/утечки из других источников). Это добавлено по явному запросу пользователя как компромисс удобство/безопасность, а не как рекомендуемая практика по умолчанию.

## Сброс (`resetVault`)

`VaultService::resetVault(path)` — безвозвратно удаляет файл хранилища (эскейп-хетч «забыл пароль и ответы — удалить всё и начать заново»). Не требует разблокировки (в этом и смысл). Восстановить данные после этого невозможно — именно поэтому UI показывает явное предупреждение перед вызовом.

## Сохранение = полное перешифрование тела (слоты — только при необходимости)

Тело не дописывается — каждое сохранение (`writeVault`) генерирует новый случайный nonce тела и переписывает файл целиком (временный файл + атомарный rename). Это исключает управление счётчиком nonce между сохранениями: 24-байтный nonce XChaCha20 безопасно генерировать случайно при каждой записи. Слоты (пароль/восстановление) пересобираются только при `changeMasterPassword`/`setupRecovery`/`disableRecovery` — обычное сохранение (после CRUD записи) их не трогает и не запускает Argon2id повторно.
